# 三层设计与取舍

## 一个总原则：能改配置就不改代码

用户给自己调语气、调频率、调压多狠，这些**不应该需要换对话**。所以：

- 所有参数在 `config.json`，每次现读，不缓存 → 改完立刻生效
- 性格在预设前缀里 → 改了要新会话（因为预设是会话创建时冻结的，见 `04-pitfalls.md`）
- 只有改**算法代码**才需要重启 DSH

这条原则决定了什么东西放哪一层。

## 三层

| 层 | 文件 | 多久变一次 | 存在哪 |
|---|---|---|---|
| 性格 | `bundles/life-preset/cordis.patch.yml` 的 `prefix:` | 几乎不变 | 系统提示词前缀，会话开头算一次 |
| 记忆 | `~/.dsh/life-mode/memory/memory.jsonl` | 每轮都在长 | 记忆图谱，按需召回 |
| 风格 | `persona/life-style.md` | 偶尔 | 每轮注入一小段 |

分开的理由是**变化频率不同**。把不变的东西塞进每轮注入，就是纯浪费。

### 为什么性格必须在前缀里

两个原因：

1. **省钱**。性格写进前缀 → 只在会话开头出现一次。写进每轮注入 → 聊 400 轮就说 400 遍。
   实测动态注入从 773 字降到 241 字，省下来的全是这个。
2. **有效**。`persona` 插件必须配 `complete: true`，否则 DSH 默认的干活型身份会和你的
   人设打架，人味被冲淡。前缀是唯一能真正覆盖默认身份的地方。

### 为什么用 MCP 记忆图谱，而不是自己写个存储

因为 `@modelcontextprotocol/server-memory` 已经是 JSONL 文件、零依赖、已经在生态里。
自己造一个存储，等于多一份要维护的格式和一个要同步的进程。我们要加的只是**旁路**：

```
memory.jsonl   图谱正文。官方 server-memory 管写
meta.jsonl     旁注：强度、分层、置顶、归档原因。我们的索引服务管
```

旁路的好处是：**官方服务升级不影响我们**，我们改评分也不影响官方写图谱。

## 为什么把压缩的决定权交给模型

这是整个项目最核心的取舍，和 `pi-midcompact` 正好相反。

它是**人审**：agent 拟草案，人来批，只有人能 commit。好处是可控，坏处是每压一次都要
打断你。

我们选**自负其责**：模型自己判断哪一段没用了，自己压。好处是聊天时不被打断，
坏处是它可能判断错。

用什么兜住判断错：

- **先记后忘**——压之前可以 `remember` 写进图谱，写失败就不压
- **只试一次**——边界不对就收手，不搞候选循环（失败不回滚，见 `02-context-folding.md`）
- **冷却 5 分钟**——防止它一轮里反复折腾
- **原始日志还在**——压缩只改「模型看到什么」，不改会话日志。真丢错东西，日志里还能翻

反过来，如果哪天想要人工审核，加个 `confirm: true` 先出草案就行。接口留着了，暂时不实现——
因为加了就把两边的优点都稀释了。

## 为什么不拆成三个独立安装包

拆开更"模块化"，但用户要的是一套能聊天的东西，不是三个半成品。所以一次装三个 bundle，
用 `-NoMemory` 表示「只要前两层」。

`config.json` 里的 `allowFold` 是另一种拆法：**只关掉压，不让关掉看**。保守的用户可以
留着 `context_map` 观察上下文，但工具表里不出现 `context_fold`，模型就压不了。
